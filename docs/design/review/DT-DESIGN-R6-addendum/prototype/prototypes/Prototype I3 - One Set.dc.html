SCHEMA THIS SHEET NEEDS
The reason travels in the link (?set=&why=&from=&task=) and is recorded on the touch, so the inventory log says why the set was handled, not just that it was. A Touch { set, reason: task_ref | why_code | 'documenting', by, started_at, ended_at, location, photos[], component_states[], measurements[], notices[], notes } is one session of handling the physical set; it is the parent of everything captured while it was in hand. Existing sheets keep their own records — Measurement (M-01) and the Set axes (I-01) are written through a touch, each carrying touch_ref as its evidence, so "how do we know the base is 16 wide" answers "James had it out on 09-18, here are the photos". Also: Set.location (with provenance), Set.components[] { name, source: instructions | operator, state: together | apart | missing }, Photo { subject, touch_ref, taken_at, by, caption }, and SetFacts { source: bricklink, fetched_at, year, pieces, theme, image } as a cached reference distinct from what we observe.
I-02 is how a set gets into I-01 (photo → read → confirm). This page is what one set looks like once it is there, and the touch is how its record grows without a separate form for each fact. Facts here are mocks; the tree's DEC-016 numbers are real.
Canonical vs. demo, on purpose. Every recorded touch is saved to this browser (append-only, keyed by set) and survives a page reload, a forced error, or clicking "Replay this touch (demo)" — replay only reopens the capture flow to run it again; it never edits or deletes a prior touch. In production this canon lives in the database behind Touch, not in the browser — this is a prototype stand-in for durable storage, chosen so dogfooding the tree unpack today keeps its data through however many demo resets this session needs.
